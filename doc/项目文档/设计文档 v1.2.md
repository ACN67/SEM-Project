# 第一部分　项目整体结构

## 1.1 建设目标与范围

建设一个可运行的 Web 应用：用户选择报告类型、产业、研究地区和时间后，系统从**预先建设的产业知识库**检索真实资料，按模板规划章节，使用大模型 API 生成分析内容，并通过程序化数据处理、引用核验和统一排版输出 Word/PDF。

**确定范围：**

- 五类必交模板：第一批产业分析、企业对标；第二批景气、招商、出海研判。
- 资料来源：管理员准备的公开产业资料，以及系统接收的 PDF、DOCX、XLSX、CSV 等文件；运行报告时只查询已入库内容。
- 智能能力：RAG 检索增强、报告大纲规划、章节生成、公文风格处理及有限并行。
- 数据能力：结构化指标计算、基础统计图表、来源关联、自动质量提示。
- 应用能力：任务状态、章节预览、可选编辑和重写、版本保存、Word/PDF 导出。
- **不承诺：**实时互联网搜索、通用网页爬虫、GraphRAG、完全自动事实证明、复杂权限系统、底层大模型训练。

**质量边界：**系统可以自动提示证据不足和明显数据矛盾；存在引用并不等于结论得到证明。不设置生成后的强制人工审批，存在警告的完整报告可按规则导出并保留警告记录。

**课程要求与交付范围。** 第 5 周验收产业分析与企业对标，第 7 周五类全部可运行，第 8–9 周统一复验。模板配置与研究重点体现可定制性；章节计划与证据包承担长文组织和内容填充；指标、图表和引用随版本交付；公文风格、Word/PDF 和版本历史通过同一份报告样例验收。

**关键解读：**知识库是写作依据；模板驱动检索与章节设计；多个独立章节可以并行请求**同一个模型 API 服务**；依赖其他章节的摘要与综合结论等待前置结果；后端负责调度，而生成模块只负责“一个章节如何写”；网页与 Word/PDF 从同一份已保存的报告版本取得内容。

## 1.3 总体运行顺序与依赖

1. **资料准备：**导入文件、解析、分块、索引、保存来源；只有可用资料进入检索范围。
2. **创建报告：**校验参数、选择模板、创建任务和报告草稿。
3. **规划大纲：**产生章节任务（问题、证据类型、图表要求、依赖），进行一次资料覆盖检查。
4. **初始化共享事实：**建立研究范围、来源清单、已确认指标和术语；生成期间可追加已核验事实，不能允许并行章节互相改写共享基线。
5. **生成正文：**对每章先按研究问题检索原始指标、计算派生指标并评估缺口，再生成和润色正文。调度器按依赖关系安排章节；不相互依赖的章节最多 2–3 个并行，后端在冻结的资料范围内准备章节证据包，生成器读取该包写作。
6. **依赖阶段：**综合分析依赖基础章节；摘要和最终结论读取全篇结果后生成，不在第一轮并行。
7. **自动检查：**对每章执行基础格式/数字/证据检查，汇总后再进行全篇一致性检查；问题以可定位的检查项记录。
8. **保存与交付：**形成不可变版本快照；用户可直接导出，或选择局部修改并生成新版本；导出永远锁定指定版本。

如果资料缺失，应对受影响章节发出明确警告或标记未完成；**不得将模型补写内容伪装成已验证事实**。必需章节无法形成有效结构时报告不得标记为“完整成功”。

## 1.4 数据存储与部署选择

| 资源 | 实现方案 | 选择依据 |
|---|---|---|
| 前端 | Vue 3 | 与开题报告一致，采用普通单页应用 |
| 后端 | Python + FastAPI | 适合模型调用、数据分析、文档工具集成 |
| 业务数据库 | MySQL | 保存报告、任务、版本、资料与指标元数据 |
| 原始文件与导出件 | 服务端独立文件目录 | 避免大文件直接进入业务数据库；数据库仅保存路径与校验信息 |
| 向量检索 | 轻量本地向量索引（Chroma） | 与 MySQL 分离职责；避免首版部署复杂检索集群 |
| Embedding | 本地 BAAI/bge-small-zh-v1.5 | 索引和查询必须使用同版本、同维度表示 |
| Word/PDF | DOCX 模板 + Python 排版库；PDF 由 LibreOffice 无界面转换生成 | 模板统一、便于版本化；转换能力需部署验证 |
| 任务执行 | 数据库存储任务 + 轻量 Worker + 并发信号量 | 可记录任务和重试；不先引入 Celery、Redis 等额外服务 |

**部署基线。** 通过环境变量配置模型服务、密钥和超时。随发布记录生成模型标识、向量模型修订、索引配置、排版模板版本及转换器版本，以固定资料执行中文检索和 PDF 导出验收。

# 第二部分　模块及细节设计

以下六个模块对应六位成员。所有“子模块”均为逻辑划分，**首版采用同一 Python 后端仓库内的模块化组件**，不是六个需要分别部署的微服务。

## 2.1 产业资料与知识库模块（王凯乐）

### 子结构图

~~~mermaid
flowchart LR
    UP[资料上传或批量导入] --> VAL[格式 / 大小 / 重复检查]
    VAL --> CONV[文本、标题、表格解析]
    CONV --> META[来源记录与结构清理]
    META --> CHUNK[按标题与语义边界分块]
    CHUNK --> IDX[Embedding 与检索索引]
    META --> MET[结构化指标登记]
    IDX --> SEARCH[关键词 / 向量检索与筛选]
    MET --> SEARCH
    SEARCH --> EVD[统一证据结果：ID、片段、来源]
~~~

### 设计决定

**资料来源与获取方式。** 首版由管理员从统计公报、行业协会报告及企业年报中选材，记录发布单位、发布日期、原始网址，再上传原文件。可用随项目准备的资料清单批量登记元数据。后续可支持管理员指定可信网址，系统保存原文快照并复用同一入库流程。网址导入作为可选扩展。报告生成只使用创建运行时冻结的资料版本。参考 [Dify 网站资料导入](https://docs.dify.ai/en/cloud/use-dify/knowledge/create-knowledge/import-text-data/sync-from-website)。

**资料获取。** 首版支持可信管理员手工准备与文件上传；允许批量导入指定本地目录。网址仅作为文档的来源元数据；不实现任意 URL 自动抓取。支持 PDF、DOCX、XLSX、CSV；扫描版 PDF、复杂图片表格先标记低质量或不支持，避免假设通用 OCR 一定准确。

**解析流程。** 根据类型使用适当解析器：PDF/DOCX 使用 Docling，表格文件使用对应结构化解析工具。保留原文件，解析内容记录文档、页码/表格编号、解析器版本；解析失败不允许处于 READY 状态。对于文档标题、表格列名丢失等问题提供解析状态和错误说明。

**分块策略。** 优先按标题—段落边界分块，必要时设置适度重叠；每段包含 doc_id、chunk_id、section_path、locator、source_date、tags、content、content_hash。不能仅依赖相似度分值判断来源质量。

**结构化指标。** 与文本检索并行存储经过整理的数值：metric_id、名称、值、单位、年份、地区、统计口径、source_chunk_id。首版优先支持从 CSV/XLSX 获得明确列名的指标，PDF 表格以可靠解析或少量准备阶段整理为主；不承诺任意扫描件自动识别。

**检索策略。** 初始方案采用向量相似度 + 年份、产业、来源类别等元数据过滤；可增加关键词检索作为回退/融合。返回 top_k 个来源片段及匹配信息，去重相同段落；没有合格候选时返回空列表和 COVERAGE_INSUFFICIENT，而不是让模型自由补全。

**索引更新与一致性。** 文件使用 SHA-256 判断重复；同名不同内容视为新版本。旧版本不立即删除，历史报告通过保存的 doc_version/chunk_id 仍能引用旧资料。资料 READY 后才能检索；替换 Embedding 模型需要重建索引。

### 最小验收

能够导入一份带表格的真实资料、保留可定位来源，并针对至少三类章节问题返回可追踪的证据；对缺失主题明确返回“无匹配证据”。

## 2.2 报告模板与文档导出模块（常珂舒）

### 子结构图

~~~mermaid
flowchart LR
    CAT[报告类型选择] --> CT[内容模板：章节结构与研究任务]
    CT --> PLAN[供生成模块规划章节]
    DOC[DOCX 样式模板] --> RENDER[文档渲染器]
    REP[指定版本的 ReportDocument] --> RENDER
    RENDER --> CIT[引用编号、图表与目录]
    CIT --> WORD[Word 文件]
    WORD --> PDF[PDF 转换]
    WORD --> RESULT[文件记录与校验]
    PDF --> RESULT
~~~

### 模板采用两层结构

**A. 内容模板（JSON/YAML，可被程序读取）：**template_id、template_version、report_type、sections。每章包含 section_key、默认标题、研究目标、必要证据类型、推荐指标、图表类型、depends_on、required。例如：

- 产业分析报告：概况、市场规模、产业链、竞争格局、政策环境、趋势与挑战、结论、摘要。
- 企业对标报告：对标范围、企业概况、经营指标、技术与业务、竞争差异、风险、结论、摘要。

- 景气报告：指标与口径、季度走势、同比增速变化、驱动证据、缺口与摘要。
- 招商报告：区域需求、目标环节、企业能力、候选匹配、限制和接洽建议。
- 出海研判报告：产品与市场界定、市场机会、进入条件、政策适用对象与时效、风险和行动建议。

**摘要和综合结论是结构上的前/后章节，但执行时依赖模板指定的基础分析章节。** 模板同时声明章节并发条件，不由模型自由决定运行拓扑。

**B. 排版模板（DOCX）：**封面、页眉页脚、标题等级、正文段落、表格样式、图注、参考文献样式。导出时以报告中间结构的数据为输入，不要求模型直接写 DOCX 或 HTML。

**模板管理。** 首版将模板文件纳入 Git 版本管理并由后端只读加载；不开发复杂的在线模板可视化编辑器。每份报告固定 template_version，模板变更不应默默改变历史报告。

**渲染规则。** 将正文/图表/引用统一转换为文档节点：引用使用源 evidence_id 统一编排最终编号，重复来源可去重；图表有标题、单位和数据来源。Word 导出必须包含段落、表格、图片和引用；PDF 从同一 DOCX 转换。目录页码可能需要转换器更新域，发布环境以转换后的 PDF 检查目录页码和中文字体。

**导出版本固定。** export(report_id, version_id, format) 只能读取对应不可变快照；不读取“当前正在修改”的工作数据。文件名包含版本号，导出失败保留报告和可重试状态。

### 最小验收

使用分别对应五类报告、包含正文、表格、图表、三条引用的样例 ReportDocument，稳定生成各模板对应的 DOCX 和 PDF，且不漏章、不丢引用。


## 2.3 智能报告生成模块（潘永健）

### 子结构图

~~~mermaid
flowchart TB
    PLAN[模板与需求] --> OUT[冻结大纲与资料版本]
    OUT --> KB[检索证据与指标]
    KB --> CALC[计算派生指标与评估缺口]
    CALC --> CTX[后端准备章节证据包]
    CTX --> GEN[按依赖生成并润色]
    GEN --> CHECK[章节检查与事实汇总]
    CHECK --> SYN[综合章节继承证据和指标]
    SYN --> QA[全文检查与保存版本]
~~~

### 关键设计：单章执行器与调度器分离

生成模块提供 plan_outline()、generate_chapter()、generate_synthesis() 等**无任务调度责任的能力接口**。它不控制全局并发、不直接修改任务状态，也不自行保存“当前报告版本”；以上均由后端负责。

**大纲规划。** 读取模板的默认章节、必需字段、研究问题和依赖，结合用户需求形成 Outline；大模型可调整子标题及写作重点，但不能删除 required 章节，不能生成循环依赖，也不能跳过证据要求。后端校验并冻结本次运行的大纲快照。

**章节研究计划。** 每章至少包含 research_questions、evidence_requirements、required_metrics、depends_on、desired_chart。它先指导知识库检索，再指导章节写作。参考 STORM 的“先明确问题、后写作”，但不引入模拟专家访谈等复杂 Agent 机制。

**资料覆盖检查。** 根据结果有无、相关性、年份/地区覆盖和模板必要指标，给出 SUFFICIENT / PARTIAL / INSUFFICIENT。它是一种辅助状态，不是事实真实度判定；不应仅以“检索到几段”认定资料充分。资料不足时可按模板允许的范围生成有依据部分并标记缺失。

**共享事实基线。** 初始化报告主题、研究范围、术语和经确认的关键指标；独立章节在同一轮并行时读取**只读快照**，不可彼此覆盖全局事实。每章完成后提供 summary 与 fact_candidates；只有经过规范化及检查的事实才能加入下一轮共享事实表。

**有限并行。** 大纲每章定义 depends_on。基础章节由后端最多 2 个并发起步（参数可改为 3）；每个章节独立发起同一服务商的 API 请求，无需多套 API Key。若某章依赖未满足，则进入 WAITING_DEPENDENCY。摘要、最终结论以及需综合基础章节的趋势分析应在依赖就绪后运行。

**章节调用协议。** 模型输入 = 固定章节任务 + 检索证据（有证据 ID）+ 本轮共享事实 + 相关前章摘要 + 输出结构约束。输出 = blocks（带 evidence_ids）、summary、fact_candidates、chart_requests、missing_evidence。尽量只传证据和摘要而非整篇前文，降低上下文成本。

**模型输出安全。** 使用 JSON Schema/Pydantic 验证结构；引用 ID 必须存在于本次检索证据集合；禁止把模型虚构的 URL 作为引用。模型原始文本仅作为内部调试产物，不能越过校验直接当作有效章节。对格式错误可以受限重试，次数由后端统一控制。

**全篇整合。** 生成模块负责提供章节摘要、查重候选和全文一致性建议；具体数字、证据有效性由质量模块核验。所有引用编号、章节次序和版面排版由模板/导出模块处理，不让模型手动编号。

### 最小验收

在固定资料和模板下可输出符合契约的完整大纲、结构化章节；无证据的引用被拒绝；基础章节可以由后端有限并行调用，依赖章节按顺序生成。

## 2.4 数据分析、图表与质量控制模块（陈易）

### 子结构图

~~~mermaid
flowchart LR
    MET[指标与来源记录] --> NORM[标准化 / 单位与口径检查]
    NORM --> CALC[确定性计算]
    CALC --> CHART[图表数据与图片]
    TEXT[章节正文和 evidence_ids] --> QA[数字、引用、完整性检查]
    NORM --> QA
    CHART --> QA
    QA --> ISS[检查结果：PASS / WARN / BLOCK]
    CHART --> REP[报告中间结构]
    ISS --> REP
~~~

### 设计决定

**指标处理。** 统一数值的数据类型和单位（如万辆、亿元、百分比），记录 period、region、metric_definition、source_evidence_id。不能在“销量”“产量”或不同统计范围之间直接换算。原始值保留，派生值通过公式获得，并保存计算说明。

**图表接口。** 只由结构化数据绘图，不让 LLM 自行补齐时间序列。首版支持折线图、柱状图、基础比较表；每个 chart 具有 chart_id、title、type、data、unit、source_metric_ids、asset_id。数据不足时返回 CHART_DATA_INSUFFICIENT，不生成虚构图表。

**自动质量检查分层：**

1. **结构检查：**必需章节是否齐全、输出 JSON 是否可解析、图表资源是否存在。
2. **来源检查：**段落引用的 evidence_id 是否存在、是否属于本次允许的资料快照；来源是否被撤销。
3. **数值检查：**识别可解析的关键数值，核对对应指标与单位/年份/地区，报告不一致的位置。无法可靠识别的数据不标为通过。
4. **全文检查：**同一指标在不同章节是否出现不一致、必需引用是否缺失、表图引用是否完整；重复内容可产生人工可读的提示。
5. **语义支持性检查（可选增强）：**模型辅助评估证据是否支持重要结论，输出“不确定”而非强行判定真伪。受 API 预算约束，不作为阻塞性交付条件。

**严重程度：**PASS 表示指定规则通过；WARN 表示证据有限、内容待核查或非关键缺陷；BLOCK 表示结构损坏、伪引用或无法形成有效必需章节。完整但带 WARN 的报告可以生成并导出，警告应在界面可见；存在 BLOCK 的报告不得标记为 COMPLETED。

**检查时机：**每章完成后先检查一次；所有章节整合后再执行全篇检查。计算结果供生成模块解释时使用，但必须通过后端协调共享，避免检查模块私自修改其他模块的草稿。

### 最小验收

提供预先计算过的 CSV 指标样例，程序产生正确增长率和图表；能够检测不存在的引用、错误年份、不同单位/值及缺失图表，并返回定位到章节的检查项。

## 2.5 后端业务与任务编排模块（叶泽晨）

### 子结构图

~~~mermaid
flowchart TB
    HTTP[FastAPI Routes] --> SVC[Reports / Sources / Exports Services]
    SVC --> DB[(MySQL：业务状态、快照与版本)]
    SVC --> QUEUE[任务记录 + Worker]
    QUEUE --> DAG[按依赖划分就绪章节]
    DAG --> SEM[并发限流：2 / 可配置 3]
    SEM --> RUN[调用单章节生成能力]
    RUN --> CHECK[调用质量检查能力]
    CHECK --> STORE[原子保存章节结果]
    STORE --> DAG
    STORE --> SNAP[汇总生成不可变版本快照]
    SNAP --> DB
    HTTP --> STATUS[查询任务、进度与错误]
~~~

### 设计决定

**单体式分层后端。** 提供统一 HTTP API；通过 Python 服务层调用知识库、生成、质量检查和导出接口。模块运行在同一代码库内，共用契约和数据库访问层，避免六份重复配置和单独部署。

**异步执行。** 创建任务后立即返回 job_id；生成在 Worker 中执行，前端轮询进度。首版采用单个持久化 Worker（或单独进程）+ MySQL 任务状态，不以 FastAPI 的进程内 BackgroundTasks 充当长期可靠队列；重启后扫描遗留 RUNNING 任务并将其转为可恢复/失败状态。是否改用 Celery/Redis 由负载验证决定，不预设。

**任务状态：**QUEUED → RUNNING → COMPLETED / COMPLETED_WITH_WARNINGS；RUNNING 的 stage 依次为 PLANNING、GENERATING、VALIDATING；任意阶段也可能 FAILED、CANCELLED。章节级状态包括 PENDING、WAITING_DEPENDENCY、RUNNING、SUCCEEDED、FAILED、SKIPPED。前端显示已完成章节数与当前阶段，不用未经测量的“AI 进度百分比”假装准确。

**调度算法：**章节依赖构成有向无环图（DAG）；调度器只启动依赖为 SUCCEEDED 的就绪章节；最大并发 2（配置上限 3）。某章失败后保留其他已成功章节，不自动清空任务；依赖它的章节转为 SKIPPED 并说明原因。统一处理服务商的速率限制、超时、取消与重试。

**重试与费用。** 对暂时网络错误、API 429/5xx 采用指数退避和最多 2 次额外重试；对格式校验失败可以重新请求一次或进入 FAILED，但不可无限重试；对数据缺失不做无意义重试。记录每次模型、输入/输出 token、耗时、费用估算及 retry_count；API Key 只在后端配置中保存，不向前端传递。API 预算为 100 元，按 3.5 节执行调用前额度检查。

**持久化模型。** 核心业务实体：documents、document_versions、chunks/索引映射、metrics、templates、reports、report_runs、chapter_runs、report_versions、exports、quality_issues、model_usage。关系型数据存 MySQL；大原文件、索引与导出件单独保存，数据库记录路径和完整性摘要。

**报告版本。** report_id 表示一个报告项目；run_id 记录一次生成流程；version_id 指向不可变 ReportDocument 快照。草稿的局部编辑产生新版本，不覆盖历史快照；同一 report 在并发编辑时使用版本检查避免覆盖。

### 最小验收

创建任务立刻返回 ID；能够并发处理 2 个章节、正确等待依赖章节、恢复/终止异常任务、按 ID 查询状态并保存不可变报告版本；失败时保留成功章节和可追踪错误。

## 2.6 前端交互界面模块（廖晨皓）

### 子结构图

~~~mermaid
flowchart LR
    HOME[任务与报告列表] --> CREATE[需求配置 + 模板选择]
    CREATE --> PROG[任务详情与章节进度]
    PROG --> READER[章节 / 图表 / 引用预览]
    READER --> EDIT[可选编辑与局部重写]
    READER --> EXPORT[选择版本与文件格式下载]
    HOME --> SOURCE[资料列表、上传与解析状态]
    EDIT --> READER
~~~

### 设计决定

**页面划分。** 提供“资料管理”“新建报告”“任务详情”“报告查看/编辑”“历史版本与下载”五类页面。复杂的可视化流程编辑器、在线 DOCX 所见即所得编辑器暂不开发。

**状态展示。** 任务列表包含 QUEUED/RUNNING/COMPLETED/FAILED 等状态；任务详情显示当前阶段、章节状态、错误原因、费用摘要和最近更新时间。进度查询首版使用轮询（例如每 2–5 秒），不强制实现 WebSocket。

**证据展示。** 正文旁显示引用标记，点击后展示文档名称、定位页码/段落、原文片段与来源 URL（如果有），并标注“证据不足”“年份冲突”等质量检查项。不要将外部 PDF 解析错误隐藏为成功。

**编辑约定。** 前端编辑对象为某个章节的结构化内容；提交 PATCH 时携带 base_version_id。后端保存新快照并返回 new_version_id；若版本已被其他操作更新，返回 409 冲突，不直接覆盖用户修改。章节重写与普通编辑使用不同操作。

**导出约定。** 前端只能请求某个已经存在的 version_id 的 Word/PDF 导出；没有导出完成前不显示“下载成功”。导出异常显示可恢复信息，保持在线报告可用。

**上传访问控制。** 管理员经服务端验证管理凭据后建立管理会话；每次上传校验会话的导入权限，未认证返回 401，无导入权限返回 403。模型密钥仅保存在后端。

**安全与边界。** 首版以可信课程演示环境为前提，不设计复杂多租户权限；但必须限制上传文件大小与格式，避免把 API Key 放到前端，避免向页面直接渲染不受控的原始 HTML。若以后开放公网访问，再补身份认证、配额和访问隔离。

### 最小验收

在不调用本地终端的情况下完成资料上传、创建报告、查看章节状态、浏览引用、按版本下载；模拟运行失败及版本冲突时有明确反馈。

## 2.7 模块设计的可行性取舍

| 决策 | 参考经验与理由 | 首版取舍 |
|---|---|---|
| 先研究问题再写章节 | STORM 强调先收集资料与形成大纲；GPT Researcher 按子主题组织详细报告 | **采用章节任务模板**，不实现模拟专家多 Agent |
| 文档解析与溯源 | RAGFlow 强调文档类型和可追溯检索；Docling 可处理布局、表格结构 | **借鉴/可复用组件**，复杂扫描件不保证完全正确 |
| 并发处理 | Dify 等工作流工具支持并行分支及错误路径 | **有限并行 + DAG 依赖**，不使用无限并发 |
| 引用编号 | 模型自由生成引用易出错 | **保存稳定证据 ID，由程序编排显示编号** |
| 统计与图表 | PDF 自动表格提取有不确定性 | **结构化指标优先**，不由 LLM 推测缺失指标 |
| 任务运行 | 完整分布式队列部署成本较高 | **单 Worker + 持久化状态**，保留替换队列能力 |
| 用户编辑 | 富文本编辑与跨版本一致性复杂 | **章节级编辑和快照版本**，不实现完整 Office 在线编辑 |

上述是针对课程资源约束作出的**方案评估**，不是外部项目保证能够在本组环境中直接运行。相关库及部署环境仍需在开发初期验证。


# 第三部分　统一数据结构与模块接口

本节定义 v1.2 的公共契约。进入并行开发后，任何共享字段或错误语义变更必须先更新 Schema、样例与契约测试。

具体字段、服务签名和 HTTP 请求响应以[接口规范 v1.0](../contracts/接口规范%20v1.0.md)及其关联的 OpenAPI、共享模型与联调样例为准。下文中的流程图和概念示例说明各模块职责。

## 3.1 通用约定

1. **唯一报告内容来源：**章节、引用、图表、质检与排版均以 ReportDocument 为准，不允许前端与导出模块各自组装另一份报告。
2. **稳定标识：**report_id、run_id、version_id、chapter_id、document_id、document_version_id、evidence_id、metric_id、chart_id、issue_id 均唯一且不依赖显示顺序。最终引用编号统一生成，不交由模型自行编写。
3. **接口技术：**前后端使用版本化 HTTP API；同一 Python 后端内部模块以 Pydantic 模型和类型化函数交接，不单独部署多个 Web 服务。
4. **输入校验：**必需字段、枚举、日期和关联 ID 都进行校验；日期采用 ISO 8601；异常返回明确 code 与描述，不用空字符串代替错误。
5. **运行与版本分离：**report_id 是长期报告标识；run_id 是一次生成过程；version_id 是不可变的报告快照。模板版本及资料来源版本随报告快照保存。
6. **引用边界：**引用只允许关联检索到的 Evidence，不接受模型自己生成的 URL、页码或“参考文献”作为权威数据。

## 3.2 核心对象定义

| 对象 | 核心字段 | 主要负责人 |
|---|---|---|
| ReportSpec | report_type, industry, region, period, focus, template_id, knowledge_base_id | 前端与后端 |
| TemplateSpec | template_id, version, sections, required, depends_on, evidence_requirements | 模板与生成 |
| Outline | chapter_id, section_key, title, order, research_questions, depends_on | 智能生成 |
| Evidence | evidence_id, document_version_id, locator, excerpt, title, published_at, source_url, score | 知识库 |
| Metric | metric_id, name, value, unit, period, region, entity_id, scope, source_evidence_id | 知识库与质量 |
| ChapterContent | chapter_id, title, blocks, summary, fact_candidates, chart_requests, missing_evidence | 智能生成 |
| Chart | chart_id, chapter_id, type, title, data, unit, source_metric_ids, asset_id | 数据质量 |
| QualityIssue | issue_id, severity, code, location, description, related_ids | 数据质量 |
| ReportDocument | report_id, run_id, version_id, template_ref, spec, outline, chapters, evidences, metrics, charts, issues | 全模块共享 |
| Job / ChapterRun | job_id, stage, status, attempt, retries, started_at, finished_at, error_code | 后端 |
| ExportArtifact | export_id, version_id, format, status, storage_path, checksum | 导出与后端 |

### 字段规则与内容顺序

ID 均为非空字符串。数组允许为空的情形列在下表，缺失数值用 null 并注明原因，0 表示实际观测值。日期使用 YYYY-MM-DD，任务时间戳含时区。默认知识库为 kb_demo。

| 对象 | 约束与默认值 |
|---|---|
| ReportSpec | industry、region、template_id 和 report_type 必填；period.from/to 为四位年份字符串且起年不晚于止年；focus 默认空数组；companies 在企业对标时至少含两个不同 ID。style 默认 official，length 默认 standard，可选 brief。 |
| TemplateSpec / Outline | 模板有整数版本及有序 sections；每项有唯一 section_key、required 布尔值和依赖键数组。冻结时映射为唯一 chapter_id，depends_on 只引用本大纲内的章 ID。拒绝缺章、悬空依赖和环。 |
| Evidence | 每条引用绑定不可变文档版本和摘录。locator 按 kind 校验：pdf 用页码（从 1 起），docx 用标题路径和段落序号，xlsx 用工作表名与单元格范围，csv 用行号与列名。source_url 允许 null。score 属于本次检索，不作为事实置信度。 |
| Metric | value 为十进制字符串；保留原始值、原单位、倍率与规范单位，货币指标记录币种；企业指标必须有 entity_id。同比只比较同主体、同期间粒度、同口径的两个值，按 (本期－基期)/基期计算，显示百分比时四舍五入至两位，原始精度保留。 |
| ChapterContent | blocks 为有序数组。paragraph 含 block_id、text、evidence_ids、metric_ids；table 含 block_id、列名和等宽行数组，数值单元格关联指标；chart_ref 含 block_id、chart_id。生成时的图表意图携带目标块 ID，装配阶段将已渲染图表绑定到该位置。无数据的非必需图用带原因的说明段落替代。 |
| QualitySummary | rules 为规则结果数组，每项含 rule_id、result（PASS、FAIL、NOT_CHECKED）及原因；issues 只记录 WARN 或 BLOCK，location 指向 chapter_id 和可选 block_id。未执行的必需规则阻止正式导出。 |
| ReportDocument | schema_version、template_ref（内容与排版模板版本）、source_version_ids、模型配置标识、质量结果和内容均随版本保存。parent_version_id 在初版为 null。图表 asset_id 解析到该版本保留的资源。 |
| Job / Export | 生成及重写任务以 job_id 轮询，run_id 关联运行输入和结果；终态返回 result_version_id 或 error。导出任务独立使用 export_id，只读指定版本；公开响应返回下载地址，服务器保存路径只在内部使用。 |

### 示例 1：创建报告请求

~~~json
{
  "report_type": "industry_analysis",
  "industry": "新能源汽车",
  "region": "中国",
  "period": {"from": "2025", "to": "2025"},
  "focus": ["市场规模", "产业链", "政策环境"],
  "template_id": "industry_analysis_v1",
  "knowledge_base_id": "kb_demo"
}
~~~

report_type 为下表五个稳定枚举。前端从模板详情读取 input_schema 并按类型展示字段。后端复用同一约束，验证 template_id 的类型与请求一致。必填字符串去除首尾空格后非空，缺字段、枚举无效或类型冲突时返回 422 和字段路径，创建任务和计费均发生在校验通过之后。模板列表只展示已部署版本。终验环境须提供五种类型。

|需求与枚举|ReportSpec 专用输入|数据处理、生成和验收|
|---|---|---|
|R01 industry_analysis|使用公共主题、地区和年度区间|A / TC01：中国新能源汽车 2022–2024 年同口径销量。三年趋势图与原表核对，缺年断开序列。|
|R02 enterprise_comparison|companies 为至少两个互异企业 ID 的数组|B / TC02：比亚迪与上汽集团 2023–2024 年研发投入。按主体、币种、期间、合并范围、定义对齐；不具可比性时列出差异。|
|R03 industry_prosperity|indicator 为观测指标 ID，granularity 固定为 quarter|C / TC03：2024 四季销量与 2023 同期。一个季度须有完整三个月或可信季度原值。先算各季同比，再比较相邻季未舍入增速；缺比较期时只报告可计算值，保留缺口。|
|R04 investment_attraction|region 为招商地区，target_segment 为必填产业链环节|D / TC04：合肥动力电池配套。候选项由企业 ID、地区需求证据、企业能力证据组成；双侧齐全才能形成匹配结论。单侧缺失列入待核实，不推断签约意愿。|
|R05 overseas_assessment|origin、target_market、product、as_of 必填；region 与目的市场一致，as_of 为 ISO 日期|E / TC05：中国纯电动乘用车进入德国。按产品、来源地、市场和截止日过滤证据，区分发布日期与生效区间，标出政策适用对象。无法判定时记录缺口。|

涉及政策判断的其他模板也要求 as_of。结构化指标以 period 和 granularity 标识观测期；year、quarter、month 分别采用 YYYY、YYYY-Qn、YYYY-MM。ReportSpec.period 仍用于选择年度范围。资料过滤和指标计算可以读取比较期，正文须标明该期用途。

### 示例 3：结构化章节

~~~json
{
  "chapter_id": "chapter_market",
  "title": "市场规模与趋势",
  "blocks": [
    {
      "type": "paragraph",
      "block_id": "p_01",
      "metric_ids": [],
      "text": "根据相关产业资料形成的示例分析。",
      "evidence_ids": ["ev_0007"]
    }
  ],
  "summary": "本章主要发现",
  "fact_candidates": [],
  "chart_requests": [],
  "missing_evidence": []
}
~~~

chart_requests 只表达画图意图，**不允许模型自行添加统计数值**；图表数据由质量模块读取 Metric 后计算。blocks 中每个 evidence_id 都必须属于本章提供给模型的候选集合。

### ReportDocument 内容约束

统一报告至少包含：报告及模板身份、用户需求、冻结的大纲、按章结构化正文、实际引用到的 Evidence 快照、指标与图表、质量提示、生成配置及版本信息。草稿保存前允许 version_id 为空；**只有持久化版本才能进入正式导出接口**。所有外键/引用 ID 必须在版本内可解析，图表引用的源指标必须存在。


### 章节证据包 ChapterInput

编排模块在创建运行时固定允许使用的 READY 资料版本清单。每章准备一次只读输入，覆盖检查、指标计算、重试、生成和质检共用同一范围。新入库材料由下一次新建运行使用。

| 必填字段 | 类型及约束 | 生产者及用途 |
|---|---|---|
| task | ChapterTask，含 chapter_id、研究问题、依赖与必需指标 | 编排模块取自冻结大纲 |
| source_version_ids | 去重的文档版本 ID 数组 | 编排模块固定检索边界 |
| evidences | Evidence 数组，可空 | 知识库提供。综合章合并前置章节实际引用的证据，保留原始定位 |
| metrics | 指标数组，可空 | 知识库提供原始值，质量模块计算派生值。每项含 metric_id、主体、期间、口径、单位、来源；派生值另含 formula_id 和 input_metric_ids |
| facts_version、facts | 事实轮次 ID 和已核验事实数组 | 后端在同一执行轮次冻结 |
| predecessors | 前置章节摘要数组，每项含 chapter_id、summary、evidence_ids 和 metric_ids | 基础章可空；其中各 ID 均须在包内解析 |
| gaps | 缺失项数组，每项含研究问题、原因和是否必需 | 编排模块汇总检索、指标缺口，按模板决定降级或阻塞 |

示例（模拟数据）：企业 A 同口径销量从 100 增至 120，质量模块先计算同比 20%，保存两个输入指标的 ID。模型写出“同比增长 20%”时，段落须关联该派生指标及来源。基期为零时返回缺口，不生成增长率；企业、单位或统计范围不匹配时不得直接计算。润色后再次核对数字、指标及引用。综合章若引用这项结论，沿用同一组指标与证据。

## 3.4 前端 HTTP API（v1）

统一前缀为 **/api/v1**。除文件上传和下载外使用 JSON。前端不直接读取数据库或访问第三方模型 API。

| 方法与路径 | 用途 | 成功结果 |
|---|---|---|
| GET /templates | 列出可用模板、版本与适用报告类型 | 200：分页模板列表 |
| GET /templates/{template_id}/versions/{version} | 指定版本的模板 | 200：TemplateSpec |
| GET /reports | 报告列表，含最近任务及当前版本 | 200：分页报告列表 |
| GET /reports/{report_id}/versions | 按创建时间倒序查询版本 | 200：分页版本列表 |
| GET /jobs/{job_id}/chapters/{chapter_id} | 查询章节状态与已通过章节检查的预览 | 200：status、content（尚无结果为 null） |
| POST /jobs/{job_id}/cancel | 取消排队中或执行中的任务 | 200：JobDetail |
| POST /jobs/{job_id}/retry | 重试可恢复的失败任务 | 202：新 job_id、原任务 ID 与查询地址 |
| POST /documents | 上传资料（multipart + 元数据） | 202：document_id、ingest_status |
| GET /documents | 查询资料及解析状态 | 200：分页文档列表 |
| GET /documents/{document_id} | 资料详情与来源定位 | 200：DocumentRecord |
| POST /reports | 创建报告任务（ReportSpec） | 202：report_id、job_id |
| GET /jobs/{job_id} | 查询生成进度及各章状态 | 200：JobDetail |
| GET /reports/{report_id} | 当前状态和版本索引 | 200：ReportSummary |
| GET /reports/{report_id}/versions/{version_id} | 指定版本内容 | 200：ReportDocument |
| PATCH /reports/{report_id}/chapters/{chapter_id} | 保存章节编辑 | 200：new_version_id |
| POST /reports/{report_id}/chapters/{chapter_id}/regenerate | 重新生成章节 | 202：job_id |
| POST /reports/{report_id}/versions/{version_id}/exports | 按版本导出 docx/pdf | 202：export_id |
| GET /exports/{export_id} | 查询导出状态 | 200：ExportSummary |
| GET /exports/{export_id}/download | 下载完成的文件 | 文件响应 |

创建任务支持 **Idempotency-Key**，避免重复点击产生重复的生成费用。章节编辑请求必须包含 base_version_id；如已有更新，返回 **409 冲突**，要求前端重新获取版本，而不是覆盖。

统一的错误结构为：

~~~json
{
  "error": {
    "code": "REPORT_VERSION_CONFLICT",
    "message": "报告已有更新，请刷新后重新操作。",
    "retryable": false,
    "details": {"current_version_id": "ver_004"}
  }
}
~~~

HTTP 语义：200/201 表示成功读取或创建，202 表示异步任务已接受；400/422 表示请求不合法，404 表示资源不存在，409 表示状态或版本冲突，413 表示文件过大，429 表示应用层限额，500/503 表示内部或下游依赖异常。

**交互约定。** 列表接收 page（默认 1）和 limit（默认 20，最大 100），返回 items、total、page、limit。所有 202 响应携带 status_url。上传表单含 file 与 metadata（标题、发布单位、发布日期、原文链接），状态按 QUEUED → PROCESSING → READY/FAILED 转移。上传限制为单文件 50 MiB。导出请求体为 {"format":"pdf"} 或 {"format":"docx"}，导出状态为 QUEUED、RUNNING、READY、FAILED；未 READY 时下载返回 409 EXPORT_NOT_READY。版本详情提供实际证据快照。

**写请求。** 创建、重写、重试和导出要求 Idempotency-Key。在同一操作及资源范围内，相同键与请求摘要复用原响应，同键异体返回 409 IDEMPOTENCY_CONFLICT；键、摘要和任务在同一事务保存。PATCH 请求包含 base_version_id 和替换后的 blocks；重写请求包含 base_version_id 与 scope（chapter 或 dependents）。前者重写目标章，后者更新过期的下游章节。提交事务须同时核对基版本及有效 attempt_id。

**任务恢复。** Worker 条件更新 QUEUED 记录领取任务，写入 attempt_id，每 15 秒续写心跳。启动时将心跳超过 90 秒的 RUNNING 任务标记 FAILED/WORKER_LOST。用户重试创建新 job，复用原冻结输入及已核验章节，为待执行章建立新 attempt。取消操作原子地封存任务并停止后续调度，旧 attempt 的返回值丢弃，已发出的请求可能计费。终态禁止继续写入；重复取消已取消任务返回现状，取消其他终态返回 409。资料缺失属于覆盖结果；临时服务故障由 Worker 统一有限重试，内部模块不叠加重试。

典型业务代码：DOCUMENT_UNSUPPORTED、DOCUMENT_PARSE_FAILED、INDEX_NOT_READY、COVERAGE_INSUFFICIENT、TEMPLATE_NOT_FOUND、INVALID_OUTLINE、INVALID_EVIDENCE_REF、MODEL_TIMEOUT、MODEL_RATE_LIMIT、INVALID_MODEL_OUTPUT、CHART_DATA_INSUFFICIENT、REPORT_VERSION_CONFLICT、EXPORT_FAILED。

**注意：**资料不足、图表指标不足通常是业务警告，不应一律当作 HTTP 500；是否阻止生成完成取决于模板必需项及 BLOCK 规则。

## 3.5 并发、失败和版本规则

~~~mermaid
flowchart TD
    A[冻结大纲与共享事实 F0] --> B[基础章节有限并行：最多 2]
    B --> C[轮次汇总：摘要与候选事实]
    C --> D[核验并形成共享事实 F1]
    D --> E[依赖章节：综合趋势与建议]
    E --> F[最后生成摘要和结论]
    F --> G[全篇质检与引用整理]
    G --> H[保存不可变报告版本 V1]
    H --> I[按 V1 导出]
    H --> J[可选编辑并保存 V2]
    J --> K[按 V2 导出]
~~~

- **数据竞争：**并行章节只读 F0；完成后提交事实候选，经检查汇总生成 F1。不得让多个协程同时无控制地修改共享事实。
- **DAG 调度：**只有 depends_on 中的章节均成功，才能调度当前章。依赖失败时保留已有结果，后续章进入 SKIPPED 并标明原因。
- **完整性：**必需章节成功且无 BLOCK 才能进入 COMPLETED 或 COMPLETED_WITH_WARNINGS；失败的必需章节使任务 FAILED，但可保留局部草稿供诊断。
- **限流：**默认最大并发 2，可配置为 3；对临时 API 错误限次退避重试；同一模型 API 服务支持多个请求，无需为章节配置多个密钥。
- **原子版本：**version_id 对应不可变快照；编辑生成 V2 后不得覆盖 V1；导出时固定指定版本。
- **重试安全：**一次重试产生新的 attempt_id；只允许当前有效 attempt 写入结果，防止超时旧请求覆盖新请求。

**预算控制。** 首份真实报告记录每章用量和耗时。达到预算的 80% 时提示组长；发起每次调用前为其最大预计费用预留额度，剩余额度不足时停止发起付费调用并记录 BUDGET_LIMIT。模型联调使用固定应答，真实调用按实测用量安排。

### 编辑、关联更新与导出

编辑和局部重写均携带 base_version_id。编排模块在保存事务中比较当前版本，冲突返回 REPORT_VERSION_CONFLICT；异步重写在领取时和提交结果时均检查。章节正文改变后，后端重做本章数值与来源检查，重算关联图表，并按冻结大纲递归标记所有下游章节为 STALE。该标记属于版本内容的新鲜度，独立于执行状态。返回 new_version_id、stale_chapter_ids、exportable。旧快照仍可按原状态读取。

界面展示受影响章节，用户可通过重写接口携带 scope=dependents，对当前版本中过期的依赖章节按拓扑顺序更新。此次操作共用一个任务，全部更新并通过全文复核后提交一个新版本。中途失败保留原版本与任务诊断。正式导出要求已保存版本、必需章节齐全、无过期章节、全文检查已完成且无 BLOCK；否则返回 409 REPORT_NOT_EXPORTABLE 和原因。WARN 随版本显示并写入导出文件。

## 3.6 联调用公共样例和契约测试

新增联调用例：同次运行中途上传新资料时，后续章节仍使用原清单；两个年度数值产生的同比在正文、摘要与图表中一致；编辑基础章后，旧版本仍可下载，新版本显示受影响的摘要并阻止正式导出；完成关联重写后恢复导出；并发编辑期间返回的旧重写结果不得覆盖新版本。

在 **shared/contracts/fixtures** 保存：report_spec.json、outline.json、evidences.json、metrics.csv、chapter_valid.json、chapter_invalid.json、report_document.json、quality_issues.json、job_states.json。

至少实现：结构校验成功/失败、缺失引用被拒绝、错误年份/单位被标记、必需章节缺失不能标为成功、DAG 无环、依赖章等待、同一章节重试不重复保存、V1/V2 编辑和导出互不覆盖。样例可以包含模拟数字，但必须标识为测试数据，不能混入真实产业资料。

## 5.2 分支、PR 与持续集成规则

**分支策略：单 main + 短期任务分支。**

- main 始终保持可启动且通过基础测试；禁止直接向 main 推送功能代码。
- 每项任务从最新 main 创建分支，示例：feature/knowledge-ingest、feature/generation-outline、feature/export-docx、fix/job-retry、docs/contracts-v1。
- 不建议六人长期维护永不合并的个人大分支；长期分叉会在最后一周产生大量冲突。
- **以可验证的进度合并，而不是最后一次性合并。** 每个模块完成一个有测试的独立子功能，就可以提交 PR；不能要求整模块全部写完才能合并。
- PR 必须描述：目的与范围、主要变更、影响接口、测试结果、关联任务及潜在风险；有界面改动可附截图。
- 至少需要 **1 名非作者审核人**批准；改动共享契约、迁移脚本或公共任务状态时，由直接受影响模块负责人参与审查，组长负责协调。
- 合并前必须通过 CI：代码格式/静态检查、核心单元测试、契约测试、至少一组关键集成测试；CI 未通过不得绕过合并。
- 推荐采用 squash merge 保持主分支提交清晰；PR 合并后删除短期分支。紧急问题使用 fix 分支补丁并保留记录。

**接口变更流程：提出变更 → 修改共享 Schema 与示例 → 通知消费者 → 更新测试 → PR 审核 → 合并。** 影响已有消费者的破坏性变更应在同一 PR 或明确的连续 PR 内提供兼容过渡，不能先在 main 破坏已有功能。

**数据库变更：**通过 migrations 脚本升级，不允许成员手动修改共享开发库后不留变更记录。涉及表结构时必须提供迁移及对应测试。大模型密钥使用环境变量，不能写入 README 或代码。

## 5.3 开发阶段与合并节点（10 周）

保留项目计划书的四阶段结构，**不新增独立的“最小链路验证”阶段**，但每个模块应在自己的开发与集成测试中持续检查接口可用性。

| 周期 | 主要目标 | 主要合并检查点 |
|---|---|---|
| 第 1–2 周：启动与设计落实 | 明确首版范围、Schema、模板、数据样例、关键技术选型和仓库规范 | 仓库初始化、契约样例、项目骨架与 CI |
| 第 3–7 周：并行开发 | 知识库、生成、质量、后端、模板导出、前端分工迭代；持续局部联调 | W5 验收 A/B 并核对四份导出件；W6 核验 C 的季度计算与 D/E 证据；W7 五类均可运行 |
| 第 8–9 周：系统集成 | 用五类真实案例测试生成、版本、引用、图表与下载，修复接口问题 | 功能冻结前完成全部核心模块整合，形成演示候选版本 |
| 第 10 周：完善交付 | 错误处理、部署、测试记录、说明文档、课程演示 | 发布 v1.0 标签，提交系统及文档 |

**资源上限：**计划每人 50 人时，六人总计 300 人时；API 预算 100 元，个人 AI 开发工具预算合计 600 元，实际支出独立记录。若功能超出资源，应优先保留知识库、五类模板、按章生成、引用、基本图表/质检与 Word/PDF 闭环，推迟精细富文本编辑、高级重排、复杂语义质检等增强项。

## 5.4 测试与交付约束

**单元测试：**资料分块、模板 DAG、数值计算、引用与格式校验、版本冲突等规则模块应使用固定数据可重复运行，不依赖真实大模型调用。

**契约测试：**共享 fixtures 由提供方与消费方共同维护；每次公共 Schema 变动必须检查所有消费者。

**集成测试：**使用固定的非敏感产业资料覆盖“上传 → 入库 → 建章 → 检索 → 生成 → 质检 → 保存 → 导出”；API 可以使用 Mock 模型应答以降低费用；真实模型的烟雾测试在限定预算内进行。

**系统验收：**五类报告全部完成正向验收，各保存 DOCX、PDF 和证据清单；所有关键数字和引用能定位来源；空检索不会产生伪造引用；多章节并发/依赖行为正确；发生超时能得到明确状态；带 WARN 的完整报告可导出；BLOCK 不会被误判为成功；指定版本的网页与导出文件一致。

**部署与资料保护：**提供启动命令、环境变量示例、测试数据说明和数据库初始化步骤。禁止将私人 API Key、真实敏感文件、缓存的大模型权重或大体积运行日志提交到仓库。仅对可信数据源开放文档导入；如以后支持任意公网 URL，必须另行设计网络访问安全与内容许可校验。

**需求与设计、测试对应。** R01–R05 逐类对应第 3.2 节 A–E 与 TC01–05。R06–R07 对应 2.1、2.5、2.6 的导入与配置（TC06–07）；R08–R10 对应 2.3、2.4 的上下文装配、计算和质检（TC08–10）；R11–R13 对应 2.2、2.5、3.5 的恢复、编辑、导出（TC11–13）。N01–N04 对应 TC14–17：单 Worker、一个生成任务、两个局域网浏览器会话及 100 份预置报告下，20 次状态查询至少 19 次在 2 秒内完成；检查无凭据上传及密钥泄漏；在 Chrome 与 Edge 复验两种导出格式；重启并替换资料后核对旧版本。测试记录填写实际环境和结果。

## 5.5 外部参考与选型依据

以下项目用于技术设计参考，**不代表本组已经复现其全部功能，也不代表必须整体安装**：

- [RAGFlow](https://github.com/infiniflow/ragflow)：复杂文档解析、分块、检索测试与可追溯证据。
- [Docling](https://github.com/docling-project/docling)：PDF/Office 文档布局与表格解析的可复用组件。
- [Dify](https://github.com/langgenius/dify)：任务编排、分支执行、异常处理和运行记录。
- [FastAPI Background Tasks 文档](https://fastapi.tiangolo.com/tutorial/background-tasks/)：轻量后台处理与长任务队列的适用边界。
